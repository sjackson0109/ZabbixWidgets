# Reference behaviour of the legacy fork (Phase 0)

Purpose: clean-room description of what the legacy fork does, so a new independent implementation can be specified and tested. This document describes behaviour only. It contains no source code, no copied identifiers presented as code, no colour values and no README wording. Line numbers refer to the files as they stand at commit 05f84ff:

- browser widget class: assets/js/class.widget.js (5,276 lines)
- server data action: actions/WidgetView.php (321 lines)
- configuration form: includes/WidgetForm.php (145 lines)
- edit-form view and script: views/widget.edit.php, assets/js/widget.edit.js
- bundled charting library: ECharts 5.4.4 (assets/js/echarts.min.js)

---

## 1. Shared data pipeline (applies to all 13 charts)

### 1.1 Server side (WidgetView.php)

1. If no host group, no host and (on template dashboards) no override host is set, the server returns empty data and stops (lines 48-64). The chart is left blank with no message.
2. Otherwise it asks the Zabbix item API for every item that matches the selected groups and/or hosts (or only the override host on a template dashboard). It requests the item id, value type, name, units, last value, last-check time (lastclock), update interval (delay), history retention period, and the owning host's name (lines 67-88).
3. Item patterns are turned into a name search: any leading "asterisk-colon" host prefix is removed, then all patterns are OR-ed with wildcards enabled (lines 90-101). There is no result limit and no explicit sort order, so item order is whatever the API returns.
4. For each item, the last value has every character except digits, dot and minus removed (line 123). An empty or missing last value is replaced with the string zero (lines 126-127).
5. Per-item metadata kept: name, first host name, units, value type, update interval, history period, lastclock (lines 131-139).
6. Only when the chart type is Temporal Line, Temporal Area, Area Rainfall, Calendar Heat Map or Candlestick does it fetch history (lines 155-165). For the other new chart types no history is fetched.
7. History fetch (lines 180-268): resolves the time period (pre-computed timestamps if present, otherwise parses the "from"/"to" strings with a generic date parser, falling back to "last hour" on any failure), then makes one history API call per matched item, oldest first, capped at 1,000 points per item.

### 1.2 Browser side (class.widget.js)

1. On each refresh, last values that look like scientific notation are converted to numbers (lines 220-260). Because the server already stripped the letter and the sign, this path practically never fires.
2. A flat list of "fields" is built, one per item: id, name, numeric value, units, host, value type, delay, history, lastclock (lines 263-290). Any item whose value does not parse as a number is silently dropped (lines 265-270).
3. The ECharts instance is created once on first content (lines 336-384), always with the library's built-in dark theme, regardless of the Zabbix theme.
4. On every refresh the chart builder for the chosen type is called (lines 448-533). A common tooltip configuration is merged on top (lines 406-446, 540-545), and the result replaces the previous options (line 567).
5. If the builder returns nothing (for example there are no fields), the code logs to the console and leaves the previous chart on screen (lines 535-538).
6. Light/dark text colours in each new builder are chosen by checking whether the page body carries a dark-theme class.
7. Series colours come from the configured base colour. Because the colour field always has a default, the default fixed palette is never used in practice; colours 2 to 10 are generated by rotating the hue of the base colour in steps of 36 degrees with small saturation and lightness nudges, repeating every 10 (lines 747-841, 932-941).

### 1.3 Value formatting rules used by tooltips and labels

- Plain numbers: scaled with K, M, G suffixes at thousands, two decimals; very small non-zero values in exponential form (lines 1060-1076).
- Units ending in bps: bits per second with decimal (1000) steps (lines 1078-1092).
- Units that are B, KB, MB, GB or TB (case-insensitive): binary (1024) bytes scaling (lines 1094-1108).
- Any unit ending in "/s" (including bytes per second): formatted as bits per second (lines 1027-1028, 1110-1113). This is a defect: byte rates are mislabelled as bit rates.
- Percent unit: two decimals and a percent sign.
- Anything else: scaled number plus the raw unit string.

## 2. The 13 chart types

Legacy display-type IDs: 15 column, 16 stacked bar, 17 doughnut, 18 bullet, 19 radar, 20 heatmap, 21 candlestick, 22 bubble, 23 gantt, 24 tree, 25 network, 26 chord, 27 calendar heatmap.

All 13 use only the field list from 1.2 (latest values) unless stated. None reads the smooth-lines option. None reads the time period except Candlestick and Calendar (indirectly, via server history).

### 2.1 Vertical column chart (ID 15) - lines 4238-4291

- Intent: compare the current value of each matched item side by side as vertical bars.
- Data: latest value only (numeric last value).
- Options read: show legend, show grid, base colour.
- Mapping: one category per item, labelled with the item name only (no host), bar height is the value, each bar gets its own generated colour. A single unnamed series holds all bars. Value labels on top are shown only when there are 10 or fewer items. Category labels are tilted when there are more than 6 items. Tooltip shows the item name and the value formatted with that item's units.
- Fabrication/guessing: never-polled items appear as zero-height bars because the server substitutes zero (WidgetView line 127). Items with the same name on different hosts produce visually identical categories with no host to disambiguate (line 4249).
- Defects: the legend can be switched on, but the only series has no name, so the legend is empty or meaningless (line 4266). Tooltip HTML is built from the unescaped item name (line 4262).

### 2.2 Stacked bar chart (ID 16) - lines 4297-4352

- Intent: per item name, show how each host contributes to a total.
- Data: latest value only.
- Options read: show legend, show grid, base colour.
- Mapping: categories along the horizontal axis are distinct item names; one stacked series per distinct host; each segment is that host's value for that item name. Despite the description comment, bars are vertical, not horizontal. Tooltip lists each host's value plus a bold total.
- Fabrication/guessing: when a host has no item with a given name, a zero is inserted for that segment (line 4319), indistinguishable from a real zero. Values with different units are stacked and summed together without any unit check (lines 4329-4331). Tooltip values are formatted as plain numbers, so units are discarded.
- Defects: unescaped host names in tooltip HTML (line 4330). Duplicate host/name pairs: only the first match is used.

### 2.3 Doughnut chart (ID 17) - lines 4357-4402

- Intent: share-of-total of the current values of the matched items, as a ring.
- Data: latest value only.
- Options read: show legend, base colour.
- Mapping: one slice per item, labelled with item name, sized by the absolute value. Slice labels show the percentage. With the legend on, the ring is shifted left and a vertical scrolling legend sits on the right. Tooltip shows name, unit-formatted value and percentage of total.
- Fabrication/guessing: negative values are turned positive before plotting (lines 4366-4370), so a negative reading appears as a positive share. Mixed units are summed into one total.
- Defects: unescaped item name in tooltip (line 4380). Show-grid is ignored (correctly, but there is no indication to the user).

### 2.4 Bullet graph (ID 18) - lines 4408-4494

- Intent: per item, show the actual value against a target and qualitative bands (good / warning / critical).
- Data: latest value only.
- Options read: show grid only. The legend option is not read and no legend is configured.
- Mapping: one horizontal row per item (item name on the vertical category axis). Three background stacked bars form the bands; a narrower bar overlaid on them shows the actual value; a thin rectangle marker shows the target.
- Fabrication/guessing (the whole scale is invented):
  - The axis maximum is 125 percent of the largest absolute value across all items, or 100 if that is zero (line 4417). Every row shares this maximum.
  - The target for each item is 110 percent of its own current value (line 4420). The code comment calls this a demo; the method's doc comment claims a different rule (80 percent of maximum), which is also not what runs.
  - Band boundaries are fixed fractions (60, 25 and 15 percent) of the invented shared maximum (lines 4422-4436). They are not derived from Zabbix triggers, thresholds or any configuration.
  - Negative values are made positive (line 4419).
- Defects: target series is a scatter with bare numbers on a chart whose vertical axis is categorical; marker placement is fragile and should be verified rather than reproduced (lines 4455-4464). Unescaped item name in tooltip (line 4474).

### 2.5 Radar chart (ID 19) - lines 4500-4563

- Intent: compare hosts across several metrics, one polygon per host.
- Data: latest value only.
- Options read: show legend, base colour.
- Mapping: each distinct item name becomes an axis; each distinct host becomes one polygon; the polygon's value on an axis is that host's value for that item name. Each axis maximum is 120 percent of the largest absolute value seen on that axis, or 100 if zero (lines 4514-4517). Round (circular) grid with 4 rings.
- Fabrication/guessing: a host lacking an item gets zero on that axis (line 4527), drawn as a real dip to the centre. Values are made positive. Axis maxima are invented headroom rather than meaningful ranges (for percentages the natural maximum would be 100).
- Defects: tooltip lists numbers without units (line 4541); unescaped host and item names in tooltip (lines 4540-4543).

### 2.6 Heat map (ID 20) - lines 4569-4638

- Intent: matrix of hosts versus item names, cell colour showing value intensity.
- Data: latest value only.
- Options read: none of the user options (not legend, not grid, not colour). The colour ramp is hard-coded.
- Mapping: columns are distinct hosts, rows are distinct item names, cell value is the absolute value. A continuous colour scale runs from the smallest to the largest value across all cells. Cell labels show only when there are 50 cells or fewer.
- Fabrication/guessing: the units of the first item are applied to every cell in the tooltip (line 4590), even if items have different units. Missing host/item pairs are left empty (correct). Values made positive.
- Defects: when all values are equal, the colour scale has zero width (lines 4581-4582, 4614-4616). Comment says rows are items and columns hosts, which matches, but labels never include units. Unescaped host and item names in tooltip (line 4596).

### 2.7 Candlestick chart (ID 21) - lines 4645-4732

- Intent: open/high/low/close summary of how each item's value moved over the selected time period.
- Data: history (clock and value) for the selected time period when available; latest value otherwise.
- Options read: show legend, show grid; time period (on the server).
- Mapping (with at least 4 history points): history is cut into consecutive buckets so that roughly 20 candles result (bucket size is the point count divided by 20, at least 1). Each candle's open is the first value in the bucket, close the last, high the maximum, low the minimum. The category label is the bucket start time shown as hours and minutes only.
- Fabrication/guessing:
  - Items with fewer than 4 history points get one synthetic candle built from the current value: open at 97 percent, low at 94 percent, high at 106 percent, close at 100 percent (lines 4677-4686). The comment calls this plus or minus 5 percent, which is not accurate either. These candles are entirely invented.
  - The method header claims it groups 4 items as open/close/low/high; that is not what the code does.
- Defects:
  - All items are poured into one single series, while time labels are de-duplicated (lines 4674-4675). With more than one item, or with a period over 24 hours, the number of candles no longer matches the number of categories and candles are drawn against the wrong labels.
  - Synthetic candles are labelled with the item name and mixed into the same axis as time labels.
  - The server never tells the history API which value type to read: it computes the right table (WidgetView line 235) but does not pass it, so the API uses its default (floating-point history). Integer (unsigned) items therefore return no history and always fall back to the synthetic candle.
  - History is capped at the 1,000 oldest points per item (WidgetView line 245), so for long periods the most recent data is missing.
  - Non-numeric history values become not-a-number candles.
  - Units are taken from the first item for all candles (line 4691). Tooltip names unescaped (line 4700).
  - A legend can be shown but the single series is unnamed.

### 2.8 Bubble chart (ID 22) - lines 4738-4797

- Intent: show items as circles whose height and size reflect value, grouped by host.
- Data: latest value only.
- Options read: show legend, show grid, base colour.
- Mapping: horizontal axis is a category per item (item name, in overall list order); vertical position is the absolute value; bubble diameter is proportional to value relative to the largest value, clamped between a small and a large size. One scatter series per host, so the legend lists hosts. The third data dimension simply repeats the value.
- Fabrication/guessing: there is no independent size metric; size duplicates the vertical value, so the chart is a decorated bar chart. Values made positive.
- Defects: each bubble's colour is chosen by host index plus position within the host (line 4765), so bubbles of the same host get different colours and do not match their legend entry. Unescaped item name in tooltip (line 4777).

### 2.9 Gantt chart (ID 23) - lines 4804-4899

- Intent: timeline bars per item, presented as tasks with a start, end and percentage progress.
- Data: latest value plus item metadata (lastclock and update interval). No history.
- Options read: show legend, base colour.
- Mapping: one row per item labelled "host: item name". The bar ends at the item's last-check time and starts one update interval earlier. The horizontal axis is normalised to 0-100 across the earliest start and latest end, with tick labels converted back to clock times. The item's current value, made positive and clamped to 0-100, is shown inside the bar as a "progress" percentage. Drawn with a custom series of rectangles.
- Fabrication/guessing (the whole chart is synthetic):
  - The item update interval is treated as a task duration (line 4819). It is parsed as a plain integer, so suffixed intervals are wrong ("1m" becomes 1 second, "1h" becomes 1 second), user macros and zero intervals (trapper, dependent items) fall back to an invented 300 seconds, and flexible/scheduled intervals are ignored.
  - Last-check time is treated as a task end (line 4818); items never checked are given "now".
  - Any value is presented as a percentage of completion (line 4821), regardless of its units.
- Defects: legend can be shown but nothing is named. Unescaped host and item names in tooltip (lines 4844-4847). Bars of one or two pixels for typical intervals make the chart mostly empty.

### 2.10 Tree diagram (ID 24) - lines 4906-4997

- Intent: hierarchy of hosts and their items with current values.
- Data: latest value only.
- Options read: none effectively (legend option is read but the legend is forced off).
- Mapping: an invented root node labelled as a collection of hosts, then one child per host, then items. Each item name is split on every full stop to form deeper levels (lines 4919-4926); the last segment holds the value and its label shows "segment: formatted value". Left-to-right layout, collapsible, initially expanded two levels deep.
- Fabrication/guessing (period-splitting hierarchy): the hierarchy is guessed from punctuation in display names. Names containing decimals, IP addresses, versions or sentences (for example a ping item naming an address, or "Load average 1.5") are broken into meaningless nodes. Intermediate nodes inherit the units of whichever item created them first.
- Defects:
  - Segments that begin with an underscore are filtered out together with their whole subtree (line 4931), so such items vanish.
  - The per-host map is a plain object, so segments that collide with built-in object property names (for example a segment literally named after a constructor or prototype property) misbehave and can corrupt shared objects (lines 4916-4926).
  - Two items whose names share a prefix (one being a leaf, the other a deeper path) merge: the node shows a value and also has children.
  - Tooltip returns the node label as HTML without escaping (lines 4957-4962).

### 2.11 Network diagram (ID 25) - lines 5004-5100

- Intent: hosts as nodes connected by relationships, in a force-directed layout.
- Data: latest value counts only; actual values are not used at all.
- Options read: show legend, base colour.
- Mapping: one node per host, node size scaled by the number of matched items on that host (clamped). An edge joins two hosts whenever they both have an item with the same name (lines 5030-5054). Pan and zoom enabled.
- Fabrication/guessing (synthetic topology):
  - Shared item names are not a relationship; any hosts linked to the same template share almost every item name, so the result is close to a complete graph with no meaning.
  - When no edges are found and there is more than one host, a star is invented with the first host in the centre (lines 5056-5065).
  - No Zabbix maps, dependencies, LLD neighbours or network-discovery data are consulted.
- Defects: uses an adjacency-focus option deprecated in ECharts 5 (line 5085). Legend can be shown but there are no categories. Edge label text is the first shared item name only and is hidden. Unescaped host names in tooltip (lines 5073-5075).

### 2.12 Chord diagram (ID 26) - lines 5106-5182

- Intent: flows between hosts drawn as ribbons around a circle.
- Data: latest value only.
- Options read: show legend, base colour.
- Mapping: hosts are the arcs. For every item name shared by two hosts, the average of the two hosts' absolute values is added to the flow in both directions (lines 5122-5140).
- Fabrication/guessing: the "flow" is invented from coincidental item-name sharing and averaged values, which has no physical meaning. If no flow results, each host gets a self-loop equal to the sum of its values (lines 5142-5149).
- Defects: the series type requested (line 5163) does not exist in the bundled ECharts 5.4.4 (registered series types are bar, boxplot, candlestick, custom, effect scatter, funnel, gauge, graph, heatmap, line, lines, map, parallel, pictorial bar, pie, radar, sankey, scatter, sunburst, theme river, tree, treemap). Setting the options throws, the error is caught and logged (line 574), and the widget stays blank or keeps the previous chart. This chart has never rendered. Tooltip names unescaped (lines 5156-5158).

### 2.13 Calendar heat map (ID 27) - lines 5188-5275

- Intent: one cell per day across a year, coloured by the day's value (activity-calendar style).
- Data: history (clock and value) for the selected time period when available; otherwise lastclock plus latest value.
- Options read: time period (server); the legend option is read but the legend is forced off.
- Mapping: for every history point of every item, the day key is computed and the absolute value is added to that day's total (lines 5200-5207). Calendar range is one calendar year: the year of the first day found, or the current year. A stepped (piecewise) colour scale runs from the smallest to the largest daily total, with separate ramps for light and dark themes. Week starts on Monday.
- Fabrication/guessing:
  - Without history, an item contributes its current value to the day of its last check (lines 5208-5216), i.e. lastclock is used as calendar data and a single reading is presented as a daily total.
  - Daily totals are sums of raw samples, so they depend on the polling frequency rather than the metric; values from different items and units are summed together.
- Defects:
  - Day keys are computed in UTC, not the user's time zone (line 5205), so evening samples land on the next day for users west of UTC and vice versa.
  - The default period (last hour) yields at most one or two coloured cells in an otherwise empty year.
  - Periods crossing a year boundary are truncated to the first year (lines 5220-5222, 5257).
  - Same history limitations as candlestick: no value-type selection (integer items return nothing), 1,000 oldest points per item.
  - Units of the first item are applied to every day (line 5227).
  - The edit form shows the legend/grid/smooth toggles for this type even though only the period matters (and that edit script is not loaded anyway, see 3.3).

## 3. General known defects

### 3.1 Data acquisition (WidgetView.php)

- Last value sanitising removes everything except digits, dot and minus (line 123). Scientific notation is corrupted (the exponent letter and sign are removed, gluing mantissa and exponent digits together), and any text value is reduced to its digits or to empty.
- Missing last values become zero (line 127) instead of "no data".
- Item search has no limit (lines 67-115); a large host group can return thousands of items.
- History is fetched once per item in a loop (lines 233-265): N API round-trips per refresh for history-backed types.
- The history table for the value type is computed but never passed to the API (line 235 versus lines 238-246), so only floating-point items return history.
- History is capped at 1,000 points per item sorted oldest-first (lines 243-245), dropping the newest data in long periods.
- Relative Zabbix time syntax that the generic date parser does not understand silently becomes "last hour" (lines 196-212).
- The action reads host tags, item tags, tag evaluation types and column overrides (lines 104-113, 143-153) that the form never defines; these branches are dead. If both tag kinds were present, the item evaluation type would overwrite the host one (lines 106 and 112).
- History is not fetched for most of the new types (only candlestick and calendar), which is correct, but the decision is a hard-coded list rather than driven by the capability map.

### 3.2 Browser widget (class.widget.js)

- Page-wide selectors: the tooltip positioner looks up the first widget container on the whole dashboard, not this widget (line 412); the popup code searches the whole document for an existing overlay and appends to the document body (lines 1231, 1344).
- Global library: relies on a single global ECharts object loaded by the module (lines 358, 2659, 2781). Another module bundling a different ECharts version on the same page would conflict.
- Theme: the chart is always initialised with the library's dark theme (line 358) while individual builders separately guess light/dark from a body class; in the light Zabbix theme this mixes dark-theme defaults with light text choices.
- Resize: the instance is resized only from the widget resize hook while active (lines 2643-2655); there is no observer for container size changes from other causes.
- Dispose: there is no destroy/clear hook; the ECharts instance, its event handlers and any tooltips appended to the document body are never disposed when the widget is removed or the dashboard page changes.
- Dead legacy graph code (lines 2752-2813) adds a new window resize listener every time it runs and never removes it; it also depends on helpers that do not exist. It is not reached by the current flow but would leak if called.
- The LLD table type replaces the chart container's content (line 1972); switching a widget from the table to any chart type without reload leaves the ECharts instance bound to a destroyed canvas.
- Tooltips use HTML and are appended to the document body with very high stacking and pointer events enabled (lines 406-446); every new builder interpolates item names and/or host names into that HTML without escaping (lines 4262, 4330, 4380, 4474, 4540-4543, 4596, 4700-4703, 4777, 4844-4847, 4959-4961, 5073-5075, 5156-5158, 5233). Item names are user-controlled (including LLD macros from discovered data), so this is an HTML/script injection path.
- No-data handling: an empty field list leaves the previous chart visible with only a console message (lines 535-538). The explicit error display helper (lines 584-606) and the capability map (lines 43-92) are declared but never used; unsupported or failing charts produce no visible message.
- Click handlers are registered but empty (lines 374-376, 570-572); every refresh removes all handlers (line 556).
- Non-numeric items are silently dropped on the client (lines 265-270) after already being mangled on the server.
- The colour-theme table (lines 105-184) keys its entries on constants that are never defined, so every entry lands on the same key; the colour-theme option does not exist in the form either. Dead code.
- Byte-per-second units are formatted as bits per second (lines 1027-1028).
- Absolute values are used in most new builders, hiding negative readings.
- Several builders invent axis headroom (125 percent, 120 percent) instead of using item ranges or configuration.

### 3.3 Form and edit script

- The edit-form script (assets/js/widget.edit.js) is not listed in the module manifest assets, so it never loads. Its logic (waiting for a page-load event that has already fired inside the dashboard dialog, and a document-wide mutation observer) would also hide the legend, grid and smooth toggles for every type except temporal line, temporal area and calendar, including types that read those toggles.
- The edit view references a unit-type field that the form does not define (views/widget.edit.php lines 92-96); the client defaults also mention configuration fields (unit type, custom config, config type, colour theme) that do not exist.
- Display-type IDs are not contiguous (there is no 7), and the drop-down order differs from ID order.
- Chart-type-specific inputs that the charts would need (targets, thresholds, ranges, dimensions, relationships, period length, aggregation function) do not exist, which is why the builders fabricate them.

## 4. Configuration fields (WidgetForm.php)

Described in form order:

1. Host groups - multi-select of host groups. Optional; restricts the item search to these groups.
2. Hosts - multi-select of hosts. Optional; restricts the item search to these hosts. Shown only on normal dashboards.
3. Host (override) - only on template dashboards; the host whose items are used, replacing the group and host filters.
4. Item patterns - required; one or more item-name patterns with wildcards; matched against item names on the selected hosts, any of the patterns may match.
5. Chart type - required single choice among 27 display types (the 14 original Monzphere types plus the 13 added ones); defaults to the gauge.
6. Colour - a base colour, defaulting to a medium blue; used for the first series and as the seed for generated colours of additional series.
7. Time period - required; defaults to following the dashboard time period, with a fallback default of the last hour. Only used by history-backed types (temporal line, temporal area, area rainfall, calendar heat map, candlestick); also shown in the widget header for those types.
8. Show legend - checkbox, on by default.
9. Show grid - checkbox, on by default.
10. Smooth lines - checkbox, off by default; only used by the original temporal types, not by any of the 13 new charts.

Not present but referenced elsewhere: unit type, colour theme, custom configuration, host/item tag filters, per-item column overrides.

## 5. Test scenarios worth covering in the new implementation

Data acquisition

1. No host group, host or override host configured: widget shows an explicit "configure hosts" state, makes no item API call.
2. Template dashboard with and without an override host.
3. Item patterns with and without a host prefix; multiple patterns; pattern matching nothing.
4. Very large result set (thousands of items): enforced limit and a visible truncation notice.
5. Item never polled (no last value): rendered as "no data", not zero.
6. Float, unsigned integer, character, log and text items: numeric types plotted, non-numeric types excluded with a visible note; unsigned integer history returned correctly.
7. Values in scientific notation, negative values, zero, very small and very large values.
8. Byte, byte-per-second, bit-per-second, percent and custom units each formatted correctly.
9. History over periods longer than 1,000 samples: newest data present (trends or aggregation used rather than truncation).
10. Relative time periods (dashboard-linked, rounded periods such as start of day/week) resolve exactly as Zabbix does.
11. History fetched only for chart types that need it, in batched API calls.

Per chart

12. Column: duplicate item names across hosts are disambiguated; more than 10 and more than 6 items; legend behaviour with a single series.
13. Stacked bar: host missing an item shows a gap, not a zero; mixed units rejected or separated.
14. Doughnut: negative value handling is explicit; all-zero data shows an empty state.
15. Bullet: target and bands come from configuration or thresholds; absent configuration produces a clear message rather than invented values.
16. Radar: host missing an axis; percentage items use a 0-100 scale; units in tooltip.
17. Heat map: all-equal values; mixed units; single host or single item.
18. Candlestick: one item and several items; period under and over 24 hours; fewer than 4 samples shows "insufficient data" instead of synthetic candles; unsigned integer items.
19. Bubble: colour per host consistent with legend; a real size dimension if offered.
20. Gantt: only offered with genuine start/end data; delay strings with suffixes, macros and zero are never treated as durations.
21. Tree: item names containing full stops, IP addresses, leading underscores, and names equal to built-in object property names render as single leaves unless an explicit hierarchy source is configured.
22. Network: no synthetic edges; zero-relationship case shows nodes only or an explanatory message.
23. Chord: either supported by the bundled ECharts version or not offered; no self-loop fabrication.
24. Calendar: user time zone day boundaries; periods spanning a year boundary; default one-hour period; aggregation (average vs sum) is explicit; no lastclock fallback.

Lifecycle and security

25. Two widgets of the same type on one dashboard: tooltips position relative to their own widget; no cross-widget DOM interference.
26. Widget resize, dashboard edit-mode resize, browser window resize, and container change without a window resize.
27. Widget deleted, dashboard page switched, and dashboard left: chart instance disposed, no leftover tooltips or listeners.
28. Switching chart type on an existing widget, including to and from the table type.
29. Item and host names containing HTML and script markup appear as literal text in tooltips, labels and legends.
30. Light and dark Zabbix themes, and high-contrast themes.
31. Refresh with data that becomes empty: previous chart is cleared and an empty state shown.
32. Another module on the page loading a different ECharts version: no conflict.
33. Edit form: toggles shown only for chart types that use them; script actually loaded in the dialog.
